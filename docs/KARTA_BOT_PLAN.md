# План: карта базы из БД в разделе «📊 Отчёты»

Цель: в боте в разделе отчётов кнопка **«🗺 Карта базы (HTML)»** — бот собирает страницу из
актуальных данных PostgreSQL и присылает файл `.html`. Все принципы карты сохраняются
(без исполняемого JS, данные → цвет/бейдж/площади считаются при сборке), принципы бота —
тоже (одно сообщение в чате, доступ только своим, аудит изменений).

---

## 0. Что есть сейчас (по результатам просмотра проекта)

**БД** (`app/db/models.py`): `landlords`, `users`, **`premises`** (`label`, `address`, `area`),
`tenants`, **`leases`** (договор: `tenant_id`, `premises_id`, `rent_amount`, `status=active|ended`),
`meters`/`meter_readings`, `charges`, `payments`, `expenses`, `settings`, `documents`,
`notifications`, `tasks`, **`adjustments`** (аудит «кто/что/старое/новое/причина»).

**Карта**: `app/karta/Karta-krasnodar.html` (картинки, контуры, CSS, JSON с данными литер) +
`app/karta/karta.py` (stdlib, без зависимостей): `load / update / apply / check`.
Сборка детерминирована и побайтно воспроизводит текущий файл (тест `tests/test_karta.py`).

**Чего в БД нет**: описаний литер (состояние, коммуникации, двери, назначение, вид, ставка,
готовность), списка помещений внутри литеры, этажей, «липких» статусов (стройка/не сдаётся/тех.).

**Расхождения, которые надо учесть:**
1. **«Одно сообщение в чате» в коде репозитория не реализовано**: хендлеры в
   `app/bot/handlers_admin.py` отвечают через `message.answer(...)` — каждый шаг даёт новое
   сообщение, «Отчёты» присылают текст с reply-клавиатурой. Если на сервере другая версия —
   её нужно влить в репозиторий; если нет — принцип вводим этим планом (шаг 4), начиная
   с раздела отчётов.
2. **В `handlers_admin.py` нет проверки доступа** (`_is_allowed` вызывается только в
   `handlers.py`): меню «Настройки», «Расход», «Отчёты» и т.д. доступно любому, кто напишет боту.
   Отчёт с картой содержит фамилии арендаторов и суммы — закрыть до выпуска (шаг 4.1).

## 1. Схема БД (миграция `0005_premises_card`)

Литера = запись `premises` (`label` = «К1», «Д», «T7»…). Добавляем поля описания и таблицу
помещений; арендатор и фактическая рента берутся из **договора**, а не дублируются.

```text
premises  (+ колонки)
  kind           text  null        -- 'tech' для T1–T9
  floors         text  not null default '1'   -- '1' | '2' | '1,2'
  status_lock    text  null        -- closed | build | tech  (только «липкие»; иначе NULL = авто)
  badge          text  null        -- свой текст бейджа (держится, пока статус не сменился)
  hint           text  null        -- «Не описано.», «Помещение без литеры.»
  state, comm, doors, purpose, look, ready   text null
  rate           numeric(10,2) null   -- ставка, ₽/м²
  rate_text      text null            -- если ставка словами («Не оценено»)
  tenant_note    text null            -- арендатор без договора в системе («Есть (уточнить)»)
  rooms_count    int  null            -- когда нет списка помещений
  -- premises.area уже есть: общая площадь, когда нет списка помещений

premises_rooms (новая)
  id, premises_id FK→premises ON DELETE CASCADE,
  pos int, area numeric(10,2) not null, note text null, floor int null
  UNIQUE(premises_id, pos)
```

**Откуда что берётся при сборке карты:**

| Поле карты | Источник |
|---|---|
| `tenant` | `Tenant.name` активного договора (`leases.status='active'`) → иначе `premises.tenant_note` → иначе «Нет» |
| `rent_fact` | `Lease.rent_amount` активного договора (если договоров несколько — сумма) |
| `rooms` / `area` | `premises_rooms` (сумма) / `premises.area` |
| `status` | **не хранится** (кроме `status_lock`): вычисляет `karta.compute_status` — есть арендатор → синий, готовность «не…» → оранжевый, иначе зелёный |
| стоимость, факт. ставка | считаются в `karta.py` |

Так цвет на карте автоматически меняется при заключении/закрытии договора — никаких
ручных правок статуса.

## 2. Первичное наполнение

Скрипт `python -m app.scripts.import_karta app/karta/Karta-krasnodar.html` (один раз, идемпотентно):
- читает JSON через `karta.load`;
- для каждой литеры находит/создаёт `premises` по `label`, заполняет поля и `premises_rooms`;
- `tenant` из JSON: если есть арендатор с таким именем и активным договором на эту литеру —
  ничего не пишет; иначе кладёт в `tenant_note` (сейчас договоров в боте может не быть);
- `status` closed/build/tech → `status_lock`;
- выводит отчёт: создано/обновлено, литеры, где `tenant_note` расходится с договором.

**Критерий приёмки:** `import → export → karta.apply(template, data)` даёт файл,
**побайтно равный** `app/karta/Karta-krasnodar.html` (тест на SQLite, как остальные).

## 3. Сервис сборки `app/services/karta_service.py`

```python
async def build_data(session, landlord_id) -> list[dict]      # БД → JSON в формате karta.py
async def render_html(session, landlord_id) -> tuple[bytes, dict]  # (файл, сводка)
```
- шаблон = `app/karta/Karta-krasnodar.html` (картинки/контуры/CSS); данные подставляет
  `karta.apply` — тот же код, что и в CLI, поэтому правила карты одни;
- порядок литер — `premises.id` (как в шаблоне); литеры, которых нет в шаблоне (нет контура),
  в сводке выводятся как «нет на плане»;
- сводка для подписи к файлу: свободно / арендовано / не готово, общая площадь,
  сумма фактической ренты, сколько литер без суммы;
- вызов `karta.check(data)` — если вдруг расхождение, в лог и в подпись «⚠️».
- рендер ~10 мс, кэш не нужен; готовый файл не храним (данные всегда свежие из БД).

## 4. Бот: раздел «📊 Отчёты» в одном сообщении

### 4.1 Доступ
Фильтр/мидлварь на `admin_router` (`_is_allowed`: `ADMIN_IDS` или активный `users.tg_id`) —
до кнопки карты.

### 4.2 Принцип «одно сообщение»
Хелпер `app/bot/ui.py`:
```python
async def show(bot, chat_id, state, text, kb)        # редактирует «экран» или пересоздаёт
async def show_document(bot, chat_id, state, file, caption, kb)
```
- `message_id` текущего «экрана» хранится в FSM-данных (`ui_msg_id`);
- `show`: `edit_message_text(ui_msg_id)`; если нельзя (сообщение — документ/старое/удалено) —
  удалить старое и отправить новое, запомнить id;
- `show_document`: удалить экран и отправить **документ с подписью и кнопками** — он и
  становится единственным сообщением; кнопка «⬅️ Назад» возвращает текстовый экран
  (документ удаляется, отправляется меню);
- входящие сообщения пользователя (`/menu`, ввод чисел) удаляются после обработки;
- reply-клавиатура главного меню остаётся (она не сообщение), разделы работают через inline.

### 4.3 Экраны
```text
📊 Отчёты                          (edit одного сообщения)
 ├ 💰 Платежи по помещениям        → текст в том же сообщении, [⬅️ Назад]
 ├ ⚡ Электричество за месяц        → текст в том же сообщении, [⬅️ Назад]
 └ 🗺 Карта базы (HTML)
      → экран: «⏳ Собираю карту…» (edit)
      → документ Karta-2026-11-12.html, подпись:
          🗺 Карта базы на 12.11.2026 14:05
          Арендовано 24 · свободно 9 · не готово 5
          Фактическая рента: 312 000 ₽ (нет суммы у 18 литер)
        кнопки: [🔄 Обновить] [⬅️ Назад]
```
«🔄 Обновить» пересобирает и заменяет документ через `edit_message_media`
(`InputMediaDocument`) — сообщение то же, файл новый.

callback_data: `rep:menu`, `rep:pay`, `rep:elec`, `rep:map`, `rep:map:refresh`.

### 4.4 Файл
`BufferedInputFile(html_bytes, filename=f"Karta-{date}.html")`, ~1,1 МБ (лимит Telegram — 50 МБ).
Открывается на телефоне в браузере (Safari 15.4+, Chrome 105+ — нужен CSS `:has`), JS не нужен.

## 5. Изменение литер через бота (следующий этап, та же основа)

Раздел «🏢 Литеры»: этаж → литера → поле → значение, всё в одном сообщении.
- поля: `state`, `comm`, `look`, `rate`, `ready`, `tenant_note`; **арендатор и рента** —
  через договор (создать/закрыть договор), чтобы карта, начисления и УПД не расходились;
- запись — `premises_service.update_field(...)` + строка в `adjustments`
  (`entity_type='premises'`, field, old/new, user) — аудит уже есть в схеме;
- после сохранения — экран литеры с пересчитанными стоимостью, факт. ставкой и статусом
  (`karta.summary`) и кнопка «🗺 Карта» для свежего файла.

## 6. Тесты
- `test_karta_import_export_roundtrip` — импорт JSON в SQLite → сборка → равенство шаблону;
- `test_map_color_follows_lease` — создать договор на «Д» → в HTML `c-busy` на обоих этажах,
  закрыть договор → `c-free`; `status_lock='build'` не меняется;
- `test_report_map_single_message` — фейковый Bot: экран редактируется, документ заменяет
  экран, «Назад» удаляет документ (в чате всегда 1 сообщение бота);
- `test_admin_router_denies_unknown_user`.

## 7. Порядок работ
1. Проверка доступа в `admin_router` (п. 4.1).
2. Миграция `0005` + модели + `premises_rooms`.
3. `import_karta` + тест побайтного равенства.
4. `karta_service` + тест цвета от договора.
5. `app/bot/ui.py` (одно сообщение) + раздел «📊 Отчёты» на inline-экранах + «🗺 Карта».
6. Выкатка: `git pull && docker compose up -d --build`, затем один раз
   `docker compose run --rm api python -m app.scripts.import_karta app/karta/Karta-krasnodar.html`.
7. Следующий этап — редактирование литер (п. 5).

## 8. Вопросы к вам перед реализацией
1. Арендаторы на карте (Котяков, Жернев, Валес…) уже заведены в боте как договоры? Если нет —
   на старте они уйдут в `tenant_note`, а «Фактическая рента» появится по мере заведения договоров.
2. Фактическая рента = сумма аренды по договору (`rent_amount`) — подходит, или нужна
   отдельная цифра (например, с электричеством/фактически оплаченная за месяц)?
3. Публичная ссылка на «живую» карту нужна? Можно добавить `GET /karta?token=…` в FastAPI —
   та же сборка, открывается в браузере без скачивания файла.
