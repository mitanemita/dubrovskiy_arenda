# Хендовер: система учёта аренды (Telegram-бот + API)

Этот файл — краткий контекст для нового чата, чтобы не пересказывать всё заново.
Читай его первым, затем при необходимости смотри код по указанным путям.

## Что это за проект
Учёт коммерческой аренды через Telegram-бот: помещения, арендаторы, договоры, счётчики,
начисления (аренда/электричество/пеня), ручная отметка оплат, расходы, отчёты, карта
базы, задачи.

Система однопользовательская по смыслу: один арендодатель (Landlord), несколько
операторов (User по tg_id из `ADMIN_IDS`). Всё живёт под одним landlord_id.

## Стек и запуск
- Python 3.11, aiogram 3.13, SQLAlchemy 2 (async, asyncpg), Alembic, APScheduler,
  PostgreSQL 16. Тесты: pytest + SQLite (in-memory).
- Docker Compose сервисы: `db`, `migrate` (alembic upgrade head), `bot`
  (Telegram + планировщик + доставка TG-уведомлений — один процесс).
- Запуск: `docker compose up -d --build`. Миграции применяются сервисом migrate.
- Первичная инициализация арендодателя/настроек — идемпотентно при старте бота
  (`app/scripts/bootstrap.py`).
- Тесты: `pip install -r requirements.txt`, затем `python -m pytest -q`.

## Ветка и деплой
- **Актуальная версия — ветка `main`.** Рабочие ветки (`claude/*`) вливаются в `main`
  через PR; сервер всегда запускает `main`.
- Деплой (сервер и Mac): `./deploy.sh` — переключает на `main`, `git pull --ff-only`,
  `docker compose up -d --build --remove-orphans` с build-args коммита/ветки/даты и
  проверяет, что в контейнере бота именно этот коммит.
- Версия: `app/version.py` — `BOT_UI_VERSION` (поднимай при каждом изменении бота) +
  `GIT_COMMIT`/`GIT_BRANCH`/`BUILD_DATE` из образа. Видна в `/start`, `/version` и в логе
  старта бота: `inline-menu-… · main@abc1234 · собрано 15.11.2026 10:00`.

## Меню бота
- Главное: 🗂 Справочники · 💼 Учёт и финансы · 📝 Задачи · ⚙️ Настройки.
- «Учёт и финансы» (`menu:finance`): 💸 Расходы · 🔢 Показания · 💰 Отметить оплату ·
  📊 Отчёты · 🗺 Карта базы.

## Структура (главное)
- `app/db/models.py` — ORM-модели (единый источник правды). Схема БД шире, чем
  используется сейчас: таблица `documents` и часть полей (`notifications.tenant_id`,
  `payments.proof_file` и т.п.) остались от снятых функций (PDF, почта, вебхуки) —
  данные на сервере не трогаем, пригодятся для отправки квитанций.
- `app/db/enums.py` — перечисления.
- `alembic/versions/` — миграции (последняя 0007: premises.litera).
- `app/services/` — вся бизнес-логика, покрыта тестами, БЕЗ Telegram:
  - `directory_service` — CRUD помещений/арендаторов/договоров/счётчиков,
    авто-занятость помещений (`_sync_occupancy`, `active_occupants`),
    правка полей (`update_*_field`, `update_lease`), удаление, реквизиты арендодателя.
  - `billing_service` — начисления (аренда/электричество/пеня). Пеня — по ставке из
    настроек (`penalty_rate`), не из договора. `sync_electricity_charges` создаёт и
    пересчитывает электричество при вводе/исправлении показаний за любой месяц;
    первое показание счётчика — начальное (расход 0).
  - `payment_service` — ручные платежи: `register_payment` + `confirm_payment`
    (разнос по начислениям), `pay_charge` (оплата одного начисления).
  - `report_service` — `payments_by_premises`, `electricity_status`,
    `tenant_payment_status` (кто оплатил/должник + телефон + что не оплачено),
    `monthly_summary` (доход/расход/электричество/должники).
  - `karta_service` — карта базы из данных БД (шаблон и расчёты — `app/karta/`).
  - `expense_service`, `adjustment_service` (аудит корректировок сумм
    начислений/расходов), `reading_service`, `settings_service`, `task_service`,
    `landlord_service`, `notification_service` / `notification_dispatch`
    (очередь Telegram-уведомлений арендодателю).
- `app/scheduler/` — `jobs.py` (логика, тестируется с фиксированной датой) и `runner.py`
  (расписание): 1-го числа — начисления аренды/электричества и фиксированные расходы;
  ежедневно — пеня по просрочке и напоминания по задачам.
- `app/bot/` — слой Telegram (тонкие обёртки над сервисами):
  - `access.py` — `AccessMiddleware`: доступ только операторам, проверяется перед
    КАЖДЫМ сообщением и нажатием кнопки (outer middleware в `runner.py`).
  - `handlers.py` — /start, /version.
  - `handlers_admin.py` — главное меню, «Учёт и финансы» (расходы + правка по месяцам,
    показания, оплата, отчёты, карта базы), настройки, задачи, правка начислений
    договора. Тут же `edit_or_send` (навигация правит текущее сообщение) и `_clip`.
  - `handlers_directory.py` — раздел «🗂 Справочники» (карточки, правка, удаление).
  - `runner.py` — сборка Dispatcher, запуск планировщика, глобальный error-handler,
    `FSMCleanupMiddleware` (удаляет сообщения пользователя во время мастеров),
    авто-bootstrap, цикл доставки TG-уведомлений.
  - `notifier.py` — отправка TG-уведомлений из очереди (кроме напоминаний по задачам).
  - `keyboards.py` — инлайн-меню (`MENU_SECTIONS`, `FINANCE_SECTIONS`, back/cancel).

## Ключевые UX-соглашения (важно соблюдать)
- Вся навигация — инлайн-кнопки под сообщением. Reply-клавиатуры НЕ используем.
- Навигация правит текущее сообщение через `edit_or_send` (не плодит сообщения).
- Мастера живут в ОДНОМ сообщении-«панели»: `_PANELS[chat]` хранит id активного
  сообщения; callbacks правят его через `edit_or_send` (пишет панель), шаги ввода
  отвечают через `wiz_reply` (правит панель по id), точки входа — `send_panel`.
  Сообщения пользователя во время FSM удаляет `FSMCleanupMiddleware`.
- Ожидание ввода (FSM) — только для непредсказуемых значений (суммы, показания,
  ИНН, названия, даты). Всё выбираемое — кнопки.
- Нумерация в списках — сквозная 1..N (НЕ по id!). Кнопка хранит id, показываем №.
- Занятость помещения — автоматическая (договор → занято; удаление/смена → свободно).
- При правках сумм — через `adjustment_service.correct_amount` (пишется аудит).
- Цвет задачи — по остатку дней до срока (`task_service.due_color_icon`).
- Напоминания по задачам в чат НЕ шлём: они копятся как «входящие» (status=queued),
  счётчик — жирной плашкой вверху меню, список — «Задачи → 🔔 Уведомления».
- Каждое изменение бота — поднимай `BOT_UI_VERSION` в `app/version.py`.

## Данные для аналитики (Power BI и т.п.)
Всё пишется в PostgreSQL, подключайся напрямую. Доходы = `charges`
(type: rent/electricity/penalty/other, period=1-е число месяца, amount,
paid_amount, status) + `payments` + `payment_allocations` (разнос платежа по
начислениям). Расходы = `expenses` (category, mode auto/manual, period, amount).
Показания = `meter_readings` (consumption). Корректировки = `adjustments` (аудит).
Связи: charge→lease→(tenant, premises)→landlord; expense→landlord. Периоды
нормализованы к 1-му числу месяца (см. `billing_service.period_start`).

## Как продолжать
- Меняешь логику → правь `app/services/*` и добавляй тесты в `tests/`.
- Меняешь UX → правь `app/bot/*`, поднимай `BOT_UI_VERSION` (`app/version.py`), прогоняй
  `python -m pytest -q`.
- Схему БД меняешь → новая миграция в `alembic/versions/` (цепочка down_revision)
  и поле в `app/db/models.py`.

## Карта базы по ссылке (с 17.11.2026)
- «🗺 Карта базы»: если в `.env` задан `PUBLIC_BASE_URL` — панель с кнопкой
  «🗺 Открыть карту» (https → Mini App внутри Telegram, http → ссылка). Страницу
  `GET /karta/<token>` отдаёт сам бот (`app/bot/karta_web.py`, aiohttp из aiogram,
  порт `KARTA_PORT`, по умолчанию 8080) и собирает её из БД при КАЖДОМ открытии.
  Токен подписан HMAC от `BOT_TOKEN` (`app/services/karta_link.py`), срок `KARTA_LINK_DAYS` (30).
- `PUBLIC_BASE_URL` пуст или Telegram отверг кнопку → как раньше, HTML-файлом
  (на части Android, напр. Samsung Fold, файл открывается как код — поэтому ссылка).
